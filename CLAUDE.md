# NUVORA AI — Instructions for Claude Code

## Product context
NUVORA AI is an Arabic-first, multilingual interactive learning platform. The first release focuses on students and learning workflows. Do not expand the scope into a generic all-purpose AI platform during the MVP.

Read these files before making changes:
1. `README.md`
2. `docs/PRODUCT_SPEC_AR.md`
3. `docs/ROADMAP.md`

## Non-negotiable working rules
1. Inspect the existing repository and current implementation before editing.
2. Never delete, replace, rename, or redesign unrelated files, routes, components, or features.
3. Make the smallest change that satisfies the request.
4. Preserve existing behavior unless the user explicitly asks to change it.
5. Before a large change, explain the plan and list affected files. Wait for approval if the change is destructive, broad, or changes product behavior.
6. Do not claim a feature works until it has been implemented and tested.
7. Do not use mock data as if it were live data. Clearly label prototypes and placeholders.
8. Keep changes in small, reviewable commits with descriptive messages.
9. Run relevant checks after each meaningful change (typecheck, lint, tests, and build where available). Report failures honestly.
10. Do not silently add paid services, subscriptions, domains, or cloud resources.

## Security
- Never place API keys, service-account credentials, payment secrets, or private tokens in client-side code.
- Use environment variables and server-side routes/functions for secrets.
- Add a safe `.env.example` containing names only, never real credentials.
- Validate and authorize all server-side requests.
- Enforce subscription limits on the server/database, not only in the browser.
- Treat uploaded files and payment proofs as private user data. Restrict access to the owner and authorized administrators.
- Never activate a paid subscription solely because an image was uploaded. Payment must be verified by an authorized administrator or a trusted payment integration.
- Do not log passwords, tokens, payment details, or sensitive file contents.

## UX and accessibility
- Arabic is the default language.
- Arabic pages must use correct RTL layout; French and English use LTR.
- Prioritize responsive mobile layouts, especially Android-sized screens, while supporting desktop.
- Keep the interface clear, fast, accessible, and consistent.
- Do not use decorative 3D effects where they do not improve learning.

## Learning experience
Choose the visualization method that fits the subject:
- Biology/anatomy: interactive 3D models where suitable.
- Physics: simulations, diagrams, and experiments.
- Chemistry: molecular models and reaction visualizations.
- Mathematics: step-by-step board, equations, and graphs.
- Geography: maps.
- History: timelines and contextual visual material.

Use properly licensed or otherwise authorized 3D assets. A model from an existing library must not be described as newly generated by AI. Provide a useful non-3D explanation when a suitable model is unavailable.

## Architecture direction
The intended direction is:
- Next.js + TypeScript + Tailwind CSS for the application.
- Firebase Authentication for identity.
- Cloud Firestore for application data and usage records.
- Firebase Storage for private uploads, subject to security rules and cost review.
- AI provider calls from server-side code only.
- Three.js / React Three Fiber for interactive 3D where appropriate.

These are proposed choices, not permission to create paid resources. Verify current compatibility, pricing, and setup requirements before implementation. Do not provision billing or deploy paid infrastructure without explicit user approval.

## Usage limits (initial proposal; configurable)
| Plan | General chat user messages/day | New study topics/day |
|---|---:|---:|
| Free | 10 | 20 |
| Plus | 50 | 50 |
| Pro | 150 | 100 |
| Max | 300 | Extended fair use |

Initial proposed monthly prices: Plus 400 MRU, Pro 900 MRU, Max 1500 MRU. Treat these as draft values until the owner confirms them and actual operating costs are tested.

Counting rules:
- Count each new user message in general chat; do not count the assistant response.
- Count a new study question/topic once. Clarifying follow-ups within that same topic should not consume additional topics.
- Enforce limits atomically on the server to prevent refresh, multi-tab, and concurrent-request bypasses.
- Store plan limits and reset settings centrally so an administrator can change them.
- Daily reset timezone/UTC behavior must be explicit and configurable.

## Payment direction (Mauritania-first; later phase)
The proposed manual flow supports Bankily and Sedad:
1. User chooses a plan and payment method.
2. Display the configured receiving account and amount.
3. User submits transaction reference and proof image.
4. Create a pending payment request.
5. Authorized admin verifies the actual transfer and approves/rejects it.
6. Activate or extend the subscription only after approval.

Prevent reuse of an already accepted transaction reference. Keep proof images private. Receiving account numbers must be configurable by an admin and must not be hard-coded in components.

Do not implement this payment flow until the owner confirms the account details, admin workflow, and legal/operational requirements.
